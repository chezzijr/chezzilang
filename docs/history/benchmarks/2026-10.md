## TICKET-264 — one print routine, variadic fn values (2026-10-17)

A direct `print` and a `print` value now go through one print routine, and a value call packs a
variadic tail like a direct call. Release binaries, base `4439afd8` vs the branch, built into two
`CARGO_TARGET_DIR`s under `~/.cache/t264/`. `hyperfine` is not installed, so the shell `time`
keyword (`TIMEFORMAT=%R`) timed 7 runs per binary, the two binaries in turn, stdout to `/dev/null`.
Wall seconds, mean ± sample standard deviation. Both binaries print the same stdout on all three
benches (same md5).

| bench | what it stresses | base `4439afd8` | branch | uptime load average (start, end) |
|---|---|---|---|---|
| `print_loop` (new) | 600000 direct prints: `print(i)`, `print(i, i)`, `print(i, sep="-")` | 0.632 ± 0.026 | 0.639 ± 0.023 | 3.38, 3.33 |

## Builtin dispatch by id (2026-10-16)

`Op::CallBuiltin`, `Op::LoadBuiltin`, `Obj::Builtin` and the other builtin carriers hold a
`Builtin` id (`base/builtin.rs`) instead of a name `String`; the VM's `do_builtin` and
`invoke_value` match the id. Release binaries, base `f4314b17` vs the change, interleaved runs of
`chezzi run` as a process, ms (`hyperfine` is not installed; a Python timer, 11-15 runs per binary).

| program | base median (min) | id median (min) |
|---|---|---|
| builtin loop (below) | 1800 (1768) | 1716 (1683) |
| `benches/chz/fib.chz` | 497 (484) | 534 (521) |
| base `f4314b17` + one unrelated `#[inline(never)]`, `fib.chz` | 516 (484) | |

The builtin loop is 5% faster. `fib.chz` calls no builtin in its hot path, and an unrelated one-line
attribute on the base moves its median 4%, so `fib` is sensitive to code layout; part of its 7% is
layout, and no profiler was available to split the rest. `loop`, `primes`, `list`, `map`, `struct`,
`closure`, `poly_method` and `enum` move between -0.7% and +1.4% (min of 7 interleaved runs).

The builtin loop:

```chezzi
fn main():
    total := 0
    i := 0
    while i < 2000000:
        c := chr(97 + i % 26)
        total += ord(c) + int(str(i % 10)) + int(float(i % 7))
        if bool(i % 3):
            total += 1
        i += 1
    xs := List[int]()
    o := ord
    j := 0
    while j < 1000000:
        xs.push(o("a"))
        j += 1
    print(total + xs.len())
main()
```

## TICKET-258 — `xs += ys` builds a new list (2026-10-14)

Owner rule U15: `x OP= v` is `x = x OP v`. `Op::AddInPlace` extended the left list in place; it is
deleted, so a loop of `xs += [i]` copies the list each time and is O(n^2). No fast path is kept:
the VM has no reference count, so it cannot prove that no alias observes an in-place extend.
`push` and `extend` are unchanged. `i += 1` and `total += i` still fuse to `IncLocal` and
`BinLocalLocal{Add}`, so integer loops are unchanged.

Release binaries, base `ea315b1c` against the prototype, 20000 appends, three runs each, load
average 9.61 (seconds):

| loop | base | branch |
|---|---|---|
| `xs += [i]` | 0.0083 to 0.0106 | 0.667 to 0.691 |
| `ys.push(j)` | 0.0067 to 0.0070 | 0.0066 to 0.0068 |

## TICKET-255 — startup of `chezzi run` after TICKET-253 (2026-10-14)

the prelude 2 times, checked it 3 times and compiled the `Range` methods, whether or not the program
held a range. The fix has three parts: the checker and the compiler skip the prelude `Range` method
bodies when `ModuleGraph::range_used` is false; `chezzi run` builds one graph (the pre-run check hands
it to the VM); `compile_graph` runs one checker pass instead of two.

includes `check`, graph build, compile and VM start, and reads about 6.5 ms before TICKET-253.

Release binaries, 300 interleaved runs per binary, median us (p10..p90). Load average about 7
(`uptime` before the run: 6.84).

## TICKET-243 — single-element writers of a shared list and set (2026-10-10)

`ConcurrentList.push` and `ConcurrentSet.add` / `remove` splice one element into the stored wire
container under the box's update guard. Before, the only way to append to a shared list or add to a
shared set was a whole-value `RwShared.write`, which decodes and re-encodes the container.

Release binary, a 100k-element container, 200 calls each, one run per row.

| operation | main `95d4e6c0` (`uptime` 1.3-1.9) | branch (`uptime` 2.86) |
| --- | --- | --- |
| list: `write` + one push | 1465 ms | (whole `write` of the list, no push: 1275 ms) |
| list: `ConcurrentList.push` | — | 16 ms |
| set: `write` + one add | 3547 ms | — |
| set: `ConcurrentSet.add` | — | 2 ms |
| set: `ConcurrentSet.remove` | — | 821 ms |
| map: `set_key` / `ConcurrentMap.set` | 3 ms | 4 ms |
| list: `at(i)` | 1 ms | 0 ms |

Notes:
- The 16 ms of `push` is one re-encode of the list plus 199 splices. A stored wire list carries no
  id ceiling, so the first `push` after a whole store decodes and re-encodes it once.
- `ConcurrentSet.remove` is O(n): it shifts the tail and rebuilds the hash index, as
  `ConcurrentMap.remove` and heap `Set.remove` do. It copies no element.
- `at(i)` is constant time. The ticket's "49 ms per 200 calls" did not reproduce on main or on the
  branch.
- Gate: `tests/chz/stdlib/concurrent_collection_perf_test.chz`, one absolute bound of 300 ms per
  200 calls.

Cells slower than their run-to-run range, each explained:

1. Whole-value copies of a big value (`Shared.get`, `RwShared.get`, `RwShared.read` at n = 1000 and
   n = 100000) cost about 1.8 times more: 4086-4912 us against 2282-2587 us at n = 100000 with one
   caller. Before, a copy cloned an already-encoded value and decoded it. Now it walks the live
   heap to encode, then decodes. This is the price of `update` no longer encoding. A caller that
   needs part of a big value uses `Shared.read(f)` (2 us) or a collection read (1.6 us).
2. `Shared.get` with 8 callers at the default worker count: 2.2-2.6 us against 0.68-0.82 us at
   n = 1. A `Shared` admits one user at a time and a reader now encodes under its lock. With the
   update guard taken on every `get` this cell measured 5.3-5.7 us; `get` now tries the state lock
   first and takes the guard only when the lock is busy. `RwShared.get` / `read` with 8 readers,
   the cell most at risk, held: 0.41-0.61 us against 0.47-0.59 us.
3. Small-value `get` / `RwShared.read` with one caller: 1.9-2.5 us against 1.5-2.0 us. Same cause

4. Box creation: `Shared(i)` plus one `get` costs 4.4-5.9 us against 0.9-1.4 us, about 4 us more

   Peak RSS of 100000 boxes created and dropped: 11.7 MB (`RwShared` 11.8 MB) against 10.8 MB.
5. `update` with an `int` state and `fn(x): x + 1`: 1.32-1.54 us against 1.21-1.52 us. The closure
   is encoded and decoded per call and the context is swapped twice; the state is not copied.
6. A closure that calls a top-level `fn` one million times: 337-355 ms against 310-327 ms per call
   of the closure (about 8 percent). Each read of a module global inside a box closure goes through
   the slot-door cache, one hash lookup.
7. A closure that calls `math.abs`: 4.2-4.5 us against 3.0-3.6 us. A qualified call reads the
   module handle, which takes the caller's view once per call.
8. Nested box calls: 4.5-5.2 us against 3.0-4.8 us for an inner top-level `fn`; 6.6-7.3 us against
   3.1-3.4 us when the inner closure reads a 100000-item global the caller does not mutate.
9. The accepted cliff: an inner closure that reads a 100000-item global the caller mutates before
   every call costs 15305-16320 us per call (two module snapshots per call) against 3-8 us. The
   one-box form of this cliff is what `spawn` pays today. Capture the value the closure needs.

## TICKET-188 — one halt predicate at every checkpoint (2026-10-01)

**Within 3% on all three checkpoint benches.** `Vm::halt_requested` (`block::halt_of`) replaced
`cancel_requested()` and the owner-fault polls. Two levers were needed to get there:

1. The owned half of the halt read (the walk over open nurseries) rides the 1-in-1024
