# Root causes — bug-hunt wave 23 (JIT sweep #8, 2026-10-11)

Sweep #8 ran five hunters on `main` at `5a3a3de4`: airlock and the new collections, scheduler and task
lifecycle, parser/names/modules, checker vs compiler, and core values plus stdlib vs CPython. Extra
weight went on TICKET-235..243. TICKET-245 merged during the sweep; the main loop re-ran every finding
below on the release binary at `9ed5f89c` (after that merge). **Not clean: 5 P0 and 9 P1.** The JIT
entry rule's "two consecutive clean sweeps" count stays at zero.

The pattern this wave: a new construct was added beside an older classifier that matched it with a
wildcard, and nothing failed to compile.
- TICKET-227 added `?x` and `!x` as `UnaryOp` variants. The airlock's name-side walk matched `Unary { .. }`
  as "an operator, result is fresh" (Family C), and the type store gave `?x` a fully free variable although
  its payload, shape and default are all known (Family B).
- Expression-valued `match` (2026-06-05) returns into the postfix loop after its DEDENT. Statement level
  learned "the previous token is a DEDENT"; the expression loops never did (Family A).
- Every operator hook added since M23 got its own hand-written "is this method the hook" in the checker
  and its own bare `run_proto` in the VM (Family D).
- TICKET-245 gave "may this joiner run other fibers on its stack" one owner and kept the fault-unwind
  site as a written exception. That exception is H2-1 (Family E).

What came out clean is in each hunter's last line, summarised at the end.

## Family A — where an indented block expression ends (A1..A4)

**Fact:** does the next line continue this expression?

**Decided in:** the postfix loop (`src/parser/mod.rs:3190`), the infix loop (`:2992`), the
comparison-chain loop (`:3011`), four comma readers (`:845`, `:857`, `:931`, `:2469`), `expect_stmt_end`
(`:568`) and `expect_member_end` (`:583`). The last two test "previous token is a DEDENT". The loops
test only `peek()`.

**Why it breaks.** The lexer emits `... Newline Dedent <first token of next line>`; no NEWLINE ever
follows a DEDENT. `parse_match_expr` (`:2058`) and `parse_recover_expr` (`:2213`) consume the DEDENT and
return into `parse_postfix`, which then sees the first token of the next line. Tokens that can start a
line and also continue an expression (`(`, `[`, `-`, `??`, and `?` in arm position) parse both ways with
different trees. Match-expression arms have no end check at all (`:2049`).

**Wrong assumption:** "the next token is not NEWLINE" means "the expression may continue".

**History.** About seven patches since `39b98d8b`, each a local test. TICKET-242 recorded nine of these
continuations as accepted drift (`BLOCK_EXPR_DRIFT`, `src/conformance.rs:747`) and DEC-242 says the
parser is not changed. That ledger compares accept/reject only, never the tree; its line 331 says "`(1)`
and `-1` on the next line are accepted by both, so they need no entry". Those are the silent cases.

**Single source.** One parser predicate, `ended_at_block()` = previous token is a DEDENT, read by the
three loops, the comma readers and the two statement-end checks (whose inline copies are deleted). Not
the lexer: it cannot tell a block-expression DEDENT from a statement-block DEDENT, and `else` / `elif`
must still follow immediately. Add the arm-end check after `:2049`.

**Effect.** After a block expression only `else:` / `else e:` / `elif` may follow on the next line, which
is what `docs/reference/grammar.bnf:754-788` already says. A scan of all 692 tracked `.chz` files found no program
that relies on any other continuation. Ledger entries 1–6 and 10–11 flip to the grammar's answer; 7–9 stay.

**Grid:** block kind {`match`, indented `recover:`, `if ... else: <block>`, closure body, prefix operand,
binary right operand} x next-line first token {`?`, `(`, `[`, `.`, `?.`, `-`, `??`, binary operators,
`|>`, `,`, `else`, `elif`} x position {`:=`, typed let, `=`, `return`, `yield`, `assert`, field default,
outer match arm, inline statement arm}; each cell asserts the parse tree, not accept/reject.

**Owner decision needed:** this reverses DEC-242's "the parser is not changed".

## Family B — the type of an un-hinted `?x` before its statement closes (B1..B6)

**Fact:** what is the type of `?5` when nothing gives it a hint?

**Decided in:** `infer_wrap_val` returns a bare `Ty::Var` (`src/checker/pattern.rs:4016`); what is known
about it (payload, carrier kind) lives in a side table read by three functions (`src/checker/tyvar.rs:29`).
Three helpers resolve it with three meanings: `zonk` (substitute only), `close_operand` (eight sites),
`pinning_value_ty` (five sites). Raw `match Ty` sites see the bare variable: `unify` (`src/checker/mod.rs:3853`),
`closed_binding_ty` (`src/checker/setup.rs:2583`), `format_spec_kind` (`pattern.rs:6228`), `sendable`
(`src/checker/proto.rs:2739`).

**Why it breaks.**
- B1: `enforce_bounds` defers the bound correctly. `close_tyvar_frame` discharges bounds (`tyvar.rs:455-464`)
  before it defaults carriers (`:465-467`), and a bound that still holds a variable is dropped with no
  error. `r: int? = dbl(?5)` is rejected correctly, because the annotation binds the variable first.
- B2: `unify(Option(Param T), Var)` binds nothing; the force in `unify_arg` runs only for an `Unknown` hole.
- B3: a lambda parameter stores the open variable; `close_operand` closes only carriers newer than its mark.
- B4, B6: `solve` binds a carrier variable to any type (`Any`, `int`, `float?`); the judge then rejects.
- B5: carriers are judged in creation order; an `Error` carrier judged before the `Present` that pins it fails.

**Wrong assumption:** an un-hinted `?x` is a free variable that any sibling may bind and nobody reads
before the frame closes. It has a known payload, a shape constraint (carrier only) and a default; none
is in the `Ty`.

**History.** Sixth patch of this class: TICKET-227 (creation, one review fix), 228, 234, 238, 239.
`docs/history/bug-hunts/w22.md` marks Family A "closed by TICKET-238"; that holds for a named binding only.
No grid crosses an inline `?x` with a bound, a `T?` parameter or a lambda parameter.

**Single source.** Four changes, three in `tyvar.rs`:
1. Obligations are never dropped: judge carriers before bounds; a bound that still holds a variable is
   re-queued to the enclosing frame; a leftover at the statement frame is an internal error.
2. A carrier variable binds only to a carrier: in `solve_at`, a pending `Present` variable meeting a
   non-carrier type becomes `Option(payload)` and the ordinary comparison answers.
3. Readers are closed by default: `unify_arg` (declared slot not a bare `T`), `closed_binding_ty` and
   `format_spec_kind` force with `pinning_value_ty`; `sendable` likewise.
4. Every `Present` carrier is judged before any `Error` carrier.

**Grid:** source {`?5` inline, `o := ?5`, `o: int? = ?5`} x consumer {bound fn for each bound kind,
`T?` parameter, `List[T?]` parameter, struct field `T?`, enum payload, lambda parameter through a
receiver and through an argument, `Any` slot, protocol slot, format spec, join with `!e` in both orders}.
Rows 2 and 3 are correct today and must not change.

**Risk.** `Ord(?NC(1))` on its own runs today and becomes "NC? does not satisfy Comparable" (matches the
named form). A same-statement form where a later sibling would pin a lambda parameter to `T!E` changes;
none is in the corpus. `tests/expected_type_grid.rs:804` pins the old B6 text.

## Family C — does this expression's result hold its operand? (C1)

**Fact:** can the result of expression E hold the object bound to name `n`?

**Decided in:** two independent AST classifiers that share no function: `fresh_shape`
(`src/checker/sig.rs:2342`, "what does this expression build") and `UseWalk` (`src/checker/fn_writes.rs:332`,
"where does this name go"), plus three hand type lists (`fn_writes.rs:1296`, `sig.rs:2777`, `fn_writes.rs:118`).

**Why it breaks.** `ExprKind::Unary { expr, .. } => self.operand(expr)` (`fn_writes.rs:360`) was written
when `UnaryOp` was `{Neg, Not}`. TICKET-227 added `Wrap` (`?x`) and `ErrVal` (`!x`); the wildcard absorbed
them. TICKET-240 taught `fresh_shape` that they hold their operand; the name-side walk kept `RootUse::Op`.
The `Root` verdict unmarks exactly the object `?buf` leaked. It composes through every arm that recurses:
`(?buf, 1)`, `[?buf]`, `H(?buf)`, `if c: ?buf else: None`, `match ?buf:`, `(?buf) ?? [9]`, an `else:`
guard, `unw(?buf)`, and a callee that does `return ?b` or `h.o = ?b`; List, Map and Set roots. All silent.

**Wrong assumption:** a `Unary` node is an operator, so its result is fresh.

**History.** Eleventh ticket on the freshness fact (137, 154, 165, 169, 170, 171, 179, 189, 190, 240).
No test contains `yield ?name`.

**Single source.** One per-node classification, `aliases_operand(kind, op) -> {Holds, Fresh, Child}`,
read by both `fresh_shape` and `UseWalk`, matching `UnaryOp` and `BinaryOp` exhaustively (no `..` on the
operator) and defaulting to "holds". `RootUse::Op` is reachable only from kinds it proves fresh.

**Grid:** leak form (every row of the table above, plus `{k: ?buf}`, `recover: ?buf`) x root type {List,
Map, Set, bytearray, tuple, struct} x route {`yield`, field store, `return` in a callee, argument} x
crossing {spawn argument, `spawn:` capture, `Executor` job}; each cell faults or is a compile error.

## Family D — is this method a hook, and how is it called? (D1..D6)

**Fact:** is method `m` of type `X` the hook for operator or protocol `P`?

**Decided in three places:**
1. The protocol matcher, `satisfies_methods` -> `method_matches` (`src/checker/proto.rs:2320`,
   `src/checker/mod.rs:3704`): arity, `is_static`, witness parameters, parameter and return types. Hooks
   that go only through it are sound (`hash`, `compare`, arithmetic, `neg`).
2. Per-operator checker helpers that re-derive it by hand and never test `is_static`: `struct_iter_elem`
   (`src/checker/sig.rs:5142`), `struct_iterable_elem` (`:5169`), `index_kv` (`:5243`), `index_set_kv`
   (`:5394`, also skips the return type), `slice_result` (`:5424`), `contains_item_ty` (`:5303`),
   `validate_eq_shape` (`:3618`). `print` has no checker decider.
3. The runtime, by name (plus arity 1 for `str`), calling `run_proto` directly at 13 sites. The ordinary
   call path's `is_generator -> alloc_generator` test is itself copied 10 times; the hook sites are the
   copies nobody wrote.

**Why it breaks.**
- D1: `Op::Yield` sets `gen_yielding`; only `generator_next` clears it. On a hook's host stack nothing
  does, so every enclosing `run_until` returns `Ok`: rc=0, no output, `recover:` and `defer` skipped.
- D2: the runtime decides "is this the display hook" by running the method and inspecting the result
  (`src/vm/stmt.rs:2900-2916`).
- D3: 1 and 2 disagree on one type: `fn index(a: int, k: int) -> int` fails `[T: Index[int, int]]` and
  is accepted by `c[2]`.
- D4 (Declarations family, `docs/history/bug-hunts/w16.md` Family 3): `hoist` is one in-order loop; it resolves
  a struct's field and method types (which ask `Hashable`) before inserting the struct's method table
  (`src/checker/setup.rs:3715-3747`). Not Hashable-specific: `Box[A]?` inside `A` with a bounded `Box`
  fails the same way. `extern_marshal_checks` in the same function already defers one such check.
- D5: the Atomic payload rule runs where the type is spelled (2 sites); a type built by substitution
  passes neither. Map and Set do not have the hole because their rule is a bound.
- D6: `for` uses `iterable_elem`; `List()`, `Set()`, `Map()` and generic recovery use the narrower `iter_elem`.

**Wrong assumption:** a method with a hook's name and about the right arity is the hook, and the
operator's handler may call it with a bare `run_proto`.

**History.** At least 20 tickets patched one copy (W6-3..3d, M23, W7-41/45/52/53/54, W8-32, W8-43, W9-3,
TICKET-146, 150, 161, 194, 197). No earlier root-cause document names this family.

**Single source.**
1. One checker decider, `hook_method(ty, protocol, method)`, implemented as the reserved protocol's
   requirement run through `method_matches`; the per-operator helpers keep only their type recovery.
2. One table from checker to runtime: per declared type, which method is the conforming hook, filled
   after `infer_returns`. It generalises `eq_struct` / `eq_enum` and deletes `binds_eq_hook`.
3. One runtime entry, `Vm::invoke_hook`, the only reader of the table, calling through the ordinary
   method-call path (`do_method_call(.., NO_IC, ..)`, `src/vm/call.rs:4351`).
4. D4: two-phase hoist; conformance obligations run from a deferred list after every type is inserted.
5. D5: the Atomic rule becomes a sealed bound that a type parameter must carry.
6. D6: the three constructors and `recover_iter_elems` call `iterable_elem`.

**Effect.** A generator `iter` works (the CPython `__iter__` idiom). A non-conforming `str` is not the
hook and no longer runs. A static method with a hook's name is not the hook; the operator reports its
ordinary "cannot iterate / index" error.

**Grid:** hook {`iter`, `next`, `index`, `slice`, `set_index`, `str`, `eq`, `hash`, `compare`, `add`,
`neg`, `contains`} x shape {conforming, generator body, static, wrong return, extra parameter, generic}
x use {operator, bound `T: P`, protocol-typed slot, intrinsic spelling `x.hash()`}; the operator and the
bound must give the same answer in every cell.

**Owner decisions (2026-10-11).** (1) A method is the hook exactly when it satisfies the builtin
protocol, `self` included; a static or wrong-shaped method with a hook's name is an ordinary method.
(2) Ranges and channels are out of scope: `0..3` is syntax that only `for`, a comprehension, a slice and
a `match` pattern accept (`r := 0..3` and `total(0..3)` are type errors), and `for v in ch` works while
`List(ch)` and `T: Iterable` reject a channel. Both are special cases beside the protocol. The owner is
designing one unified rule for range values, slices (`a..b` and `a:b`) and channel iteration; no ticket
patches them until that design exists.

## Family E — a nursery owner leaving by a fault (E1, E2)

**Fact:** may a joiner run other fibers on its own stack while it waits for its family?

**Decided in:** the `Nursery` row of `block::mode`, read by `Vm::joiner_helps` (`src/vm/block.rs:464`)
and `Vm::joiner_shell` (`src/vm/sched.rs:2513`) since TICKET-245. `joiner_helps` returns true for a
`Park` joiner at an inline wait; its doc keeps the residual in words.

**Why it breaks.** `return`, `break`, `continue` and `?` out of a fiber-owned nursery park
(`park_escaped_abort`, `sched.rs:659`). A fault cannot: there is no op to rewind, so
`abort_fiber_owned_nursery` (`sched.rs:1656`) runs the worker loop on the owner's stack. That loop takes
any runnable fiber and tests "family done" only when the queue is empty (`src/vm/mod.rs:4166`); a
preempted spinner is re-run without that test (`sched.rs:2667`). Two shapes: an unrelated busy fiber
(the fault waits for it) and an ancestor popped onto the owner's stack (neither can finish; DEC-103's
residual verbatim). Cancel takes the same site, so a cancelled owner inside its own nursery stalls too.

Measured, ms until the owner observes the exit, two 1 s spinners beside it, T=1 / 2 / 4:

| exit | spawned fiber | Executor job |
|---|---|---|
| normal join | 1 / 0 / 0 | 0 / 0 / 0 |
| `return` out | 2 / 1 / 1 | 2 / 1 / 1 |
| body fault (recovered) | 1000 / 1000 / 1 | 1000 / 1000 / 1000 |
| child fault (recovered) | 1000 / 1000 / 1 | 1000 / 1000 / 1 |
| cancel | 1000 / 1000 / 1 | 1000 / 1000 / 1 |

E2 is a separate site: `src/vm/stmt.rs:225-229` keeps the module nursery out of the fault teardown
("silent, as in the interp"). The rule dates from when top-level tasks were queued until the join; eager
start made them live fibers with registered `defer`s. Nine sentences of `docs/reference/concurrency.md` say the
top level is a body like any other.

**Wrong assumption:** whatever an inline-waiting owner's thread picks is harmless, and the wait ends
when the family ends.

**Single source.** The fact already has its owner; it lacks one input: "is this joiner at an op that
can rewind". Two routes:
- (a) the recorded design (DEC-103, DEC-132): a parking abort, the fault re-raised at resume over
  `Fiber::resume_native`. Costs no thread; needs a stage marker for the two sites that have already
  popped handler state (`src/vm/exec.rs:1786`, `src/vm/stmt.rs:318`).
- (b) route the fault site to `hand_joiner_slot`: small diff, but it is the replacement runner beside the
  deadlock verdict for a joiner that can park, which false-faulted `i6n2` twice (DEC-125, DEC-131); one
  OS thread per cancelled owner in a wide tree; a refused thread re-opens the hang.

Recommended: (a). E2: delete the `is_toplevel` branch on the floor.

**Grid:** exit {join, `return`, `break`, body fault, child fault, cancel, a `do_return` whose defer
faulted} x owner {main, spawned fiber, Executor job, fiber in a callback, fiber in `defer:`, module top
level} x neighbour {none, bounded busy sibling, runnable ancestor} x T {1, 2, 4, default}, with an
elapsed-time bound; plus the verdict samples of TICKET-245 at n >= 20, debug and release. No existing
grid puts a runnable fiber beside an aborting owner.

## Family F — walks that enter a box (F1, F2)

Both sites are deleted or rewritten by TICKET-246 (private heap per box). They belong in that ticket as
requirements and grid cells, whichever way its two open questions are answered.

**F1.** The display walk guards heap cycles with `repr_active` (keyed on `GcRef`) and a depth budget. At a
box it hands off to `display_wire` (`src/vm/stmt.rs:2459`), which has neither and holds the box lock while
it recurses: a `Mutex` re-lock hangs, an `RwLock` re-read recurses until the stack overflows. `==`,
crossing, GC mark and the byte walk are fine; the last two already key a visited set on the core's `Arc`.
Single source: every walk that enters a box consults one visited set keyed on core identity, carries the
depth budget, and never holds one core lock while taking the next. Cell: box holds itself x {`print`,
`str()`, interpolation, format spec, assert message} x {Shared, RwShared, Atomic, ConcurrentList}.

**F2.** The four walk primitives carry a raw index across lock releases (`src/vm/netio.rs:3651-3973`);
`remove` shifts the tail. `rwshared_probe` beside them restarts on `core.generation`; the walks never
